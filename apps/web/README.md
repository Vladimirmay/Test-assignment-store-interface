# @checkout/web

Фронтенд магазина для тестового задания. React 18 + TypeScript + Vite, React Router, TanStack Query, react-hook-form.

## Запуск

Нужен поднятый API (см. корневой [README](../../README.md)).

```sh
npm ci
npm run dev -w @checkout/web
```

Открывается на [http://localhost:5173](http://localhost:5173), обращается к API на `http://127.0.0.1:4000` (меняется переменной `VITE_API_BASE_URL`).

Сборка и предпросмотр:

```sh
npm run build -w @checkout/web
npm run preview -w @checkout/web
```

## Как устроена работа с API

- `src/api/client.ts` — единственное место с `fetch`: адрес, заголовки, `Idempotency-Key`, таймаут запроса. Разбирает статус, пустое тело и JSON, ошибки любого типа (сеть, HTTP, битый ответ) приводит к одному классу `RequestError`. Компоненты получают только типизированные данные или готовую ошибку, `Response` не видят никогда.
- `src/api/endpoints.ts` — по одной типизированной функции на каждый эндпоинт, поверх `client.ts`. Типы берутся из `@checkout/contracts`; то, что пакет не экспортирует как тип (например `Session`), описано вручную в `src/api/types.ts`.
- `src/queries/*` — обёртки над TanStack Query. Здесь и кэш, и инвалидация после мутаций (заказ создался — обновилась корзина), и поллинг статуса заказа/оплаты. Сам поллинг (интервал, условие остановки) вынесен в один хелпер `src/lib/polling.ts`, а не повторён в каждом хуке.
- `src/components/PaymentPanel.tsx` — весь цикл тестовой оплаты картой в одном компоненте: старт попытки, выбор карты, оплата/отмена, ожидание результата, повтор новым ключом идемпотентности после отказа или отмены. Используется и сразу после оформления заказа, и на странице заказа при возврате — код повтора не продублирован.
- `src/lib/applyServerFieldErrors.ts` — единственное место, которое раскладывает `error.fields` от API по полям формы; сами формы ошибку не разбирают.
- `src/ui/ErrorBanner.tsx`, `src/ui/Loading.tsx` — общие компоненты состояний загрузки/ошибки с кнопкой повтора, переиспользуются на всех страницах.

Кто за что отвечает: `client.ts` — транспорт, `endpoints.ts` — что именно вызывать и с какими типами, `queries/*` — когда вызывать и как кэшировать, компоненты — только отображение готовых данных.

## Обработка данных

`CatalogPage` на каждый рендер сопоставляет товары с их количеством в корзине. Первая версия делала `cart.items.find(...)` прямо внутри `products.map(...)` — при N товарах и M позициях в корзине это O(N·M) сравнений, и повторяется на каждое изменение корзины (рендер каталога довольно частый). Заменил на `Map`, которая строится один раз через `useMemo` от `cart.data` (`new Map(items.map(i => [i.productId, i.quantity]))`), а количество товара достаётся через `.get(id)` — O(N+M) на построение вместо O(N·M), O(1) на каждое обращение вместо линейного поиска. `Map` пересобирается только когда действительно меняются данные корзины (ссылка от React Query стабильна между рендерами), а не на каждый рендер компонента.

## Что проверено вручную

- Каталог: загрузка, товар без остатка, блокировка кнопки при достижении лимита остатка.
- Корзина: изменение количества, удаление, итог всегда с сервера.
- Оформление: самовывоз и курьер (стоимость доставки и итог — из расчёта на сервере), невалидные поля не отправляются и подсвечиваются под нужным полем.
- Оплата картой: успех, отказ, отмена; после отказа и после отмены — повторная попытка новым ключом идемпотентности, которая проходит.
- Наличные при получении — заказ подтверждается сразу, без формы оплаты.
- Двойной клик по «Оформить заказ» — создаётся один заказ, не два.
- Обрыв API (остановил процесс) — понятная ошибка с кнопкой «Повторить», после восстановления API страница загружается заново без потери контекста.
- Перезагрузка страницы заказа — статус и данные восстанавливаются с сервера, а не из локального состояния.
- Вёрстка на 1280 и 390px — без горизонтальной прокрутки, поля и кнопки доступны.

## Известные недоработки

- Нет автоматических тестов на фронтенде (unit/e2e) — только сценарии выше, проверенные вручную.
- Конфликт версии корзины и просроченный расчёт (`CART_VERSION_CONFLICT`, `QUOTE_EXPIRED`) обрабатываются в коде (обновление корзины и повторный расчёт), но не проверены вживую — сложно воспроизвести конфликт без второй параллельной сессии.
- Команды запуска и сборки фронтенда не встроены в корневые `npm run dev` / `npm run build` — задание позволяет описать их отдельно здесь, что и сделано.
