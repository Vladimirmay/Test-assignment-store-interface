# @checkout/web

Фронтенд магазина: React 18 + TypeScript + Vite, React Router, TanStack Query.

## Запуск

Из корня репозитория (нужен уже поднятый API, см. корневой [README](../../README.md)):

```sh
npm ci
npm run dev -w @checkout/web
```

Откроется на [http://localhost:5173](http://localhost:5173) и обратится к API на `http://127.0.0.1:4000` (переопределяется переменной `VITE_API_BASE_URL`).

Сборка и предпросмотр:

```sh
npm run build -w @checkout/web
npm run preview -w @checkout/web
```

## Устройство

- `src/api/client.ts` — единственное место, которое делает `fetch`: базовый адрес, заголовки, `Idempotency-Key`, разбор `data`/ошибки. Компоненты получают типизированные данные или уже нормализованную ошибку (`RequestError`), но никогда сырой `Response`.
- `src/api/endpoints.ts` — типизированные функции по одной на ресурс API, поверх `client.ts`. Типы данных берутся из `@checkout/contracts`, кроме тех, что пакет не экспортирует как TS-тип (например, `Session`) — они описаны в `src/api/types.ts`.
- `src/queries/*` — обёртки над TanStack Query: кэш, инвалидация после мутаций (`useSetCartItem`, `useRemoveCartItem`, создание заказа очищает кэш корзины и т.д.), поллинг статуса оплаты и заказа через `refetchInterval` — React Query сам останавливает его после того, как оплата завершилась или пользователь ушёл со страницы.
- `src/session/SessionProvider.tsx` — создаёт гостевую сессию при первом заходе и хранит токен в `localStorage`; страница заказа (`/orders/:id`) читает состояние с сервера заново при каждой загрузке, это и есть восстановление после перезагрузки.
- `src/components/PaymentPanel.tsx` — один компонент для всего цикла тестовой оплаты картой (старт попытки, выбор карты, оплата/отмена, поллинг, повтор новым ключом идемпотентности после отказа/отмены). Используется и сразу после оформления, и на странице заказа при возврате — логика повтора не продублирована.
- `src/lib/applyServerFieldErrors.ts` — единственное место, которое сопоставляет `error.fields` от API с полями формы (`react-hook-form`); формы не разбирают ошибку сами.
- `src/ui/*` — общие компоненты состояний (`Loading`, `ErrorBanner`), чтобы загрузка/ошибка не описывались заново в каждой странице.

## Статус

Готово: каталог (загрузка, недоступный товар, превышение остатка), корзина (изменение количества, удаление, итог с сервера), оформление заказа (контакты, самовывоз/курьер с расчётом стоимости с сервера), оплата тестовой картой (успех, отказ, отмена, повтор) и наличными, страница заказа с восстановлением после перезагрузки.

Не проверено отдельно: поведение при потере сети посреди запроса (idempotency-key переживает автоповтор React Query, но живого теста обрыва соединения не делал), очень быстрый двойной клик по кнопкам (защищены `disabled` при `isPending` и ключом идемпотентности на сервере, но не гонял намеренно).

## Обработка данных

`CatalogPage` на каждый рендер сопоставляет список товаров с количеством этого же товара в корзине. Изначальная реализация делала `cart.items.find(...)` внутри `products.map(...)` — то есть на N товаров и M позиций в корзине это O(N·M) сравнений на каждый рендер каталога (рендер идёт при любом изменении корзины, то есть довольно часто). Заменил на `Map`, построенную один раз через `useMemo` от `cart.data` (`new Map(items.map(i => [i.productId, i.quantity]))`), и обращаюсь к ней через `.get(id)` — O(N+M) на построение и O(1) на каждое обращение вместо линейного поиска на каждый товар. Промежуточных массивов и лишних проходов по каталогу это не добавляет: сам `Map` пересобирается только когда меняется `cart.data` (ссылка приходит от React Query и стабильна, пока сервер не вернул новые данные), а не на каждый рендер.
